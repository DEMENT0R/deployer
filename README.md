# Deployer Panel

Веб-панель для полуавтоматического развёртывания фича-веток на тестовые инстансы.

Тестировщик открывает инстанс, выбирает ветку из списка, подтянутого с git-remote, и жмёт кнопку.
Панель выполняет шаги `git` / `composer` / `migrate` / `frontend` в каталоге целевого проекта через
воркер очереди и стримит вывод обратно на страницу.

Стек: Laravel 12, Inertia 2 + Vue 3, Tailwind, очередь на БД, по умолчанию SQLite.

## Как это работает

```
браузер                  приложение                   воркер очереди            каталог проекта
  |  выбор ветки  ------> BranchController ---------------------------------> git for-each-ref (кэш)
  |  кнопка деплоя ─────> DeployController
  |                        └─ Deployment (pending) ──> DeployInstanceJob
  |                                                     └─ лок deploy:instance:{id}
  |                                                     └─ InstanceDeployer ──> git / composer / migrate / npm
  |  <-- поллинг 3с ------ deployment.status/steps/output <── чанки вывода
```

- **Instance** — развёрнутая копия какого-то проекта на диске (путь + git-remote + команды по шагам).
- **Deployment** — один запуск: выбранное действие, ветка, статусы шагов, код возврата, полный вывод.
- Одновременно на инстансе может идти только один деплой: контроллер отклоняет новый, пока есть запись
  в статусе `pending`/`running`, а джоба дополнительно берёт кэш-лок (`deploy:instance:{id}`).
- Эндпоинт деплоя ограничен 10 запросами в минуту на пользователя.

Git-шаг — ровно это:

```
git fetch --all
git stash push --include-untracked --message "deployer auto-stash <время>"   # если рабочее дерево грязное
git checkout <ветка>
git pull <remote> <ветка>
```

Stash делается только при непустом `git status --porcelain` и отключается через `DEPLOYER_AUTO_STASH=false`.
Изменения не теряются — лежат в `git stash list` целевого проекта, забрать можно `git stash pop`.
Игнорируемые файлы (`.env`, `vendor`, `node_modules` целевого проекта) не трогаются.

Список веток берётся из `git for-each-ref refs/remotes/<remote>/` и кэшируется на
`DEPLOYER_BRANCH_CACHE_TTL`. Кнопка ↻ на странице инстанса выполняет `git fetch --all` и обновляет кэш;
кэш также сбрасывается после успешного деплоя `full`/`branch`.

Ветки отсортированы **по свежести** (`--sort=-committerdate`), рядом с именем показано, когда в неё
последний раз коммитили. Сортировка и дата берутся из локальных remote-tracking ссылок, поэтому
актуальны на момент последнего `fetch`. Сортирует git, а не PHP — порядок обязан совпадать с датой.

## Возможности

- Реестр инстансов: путь, remote, ветка по умолчанию и свои команды на каждый шаг
- Выбор ветки из списка с git-remote, с ручным обновлением
- Действия деплоя (полный / только ветка / composer / кэши / миграции / фронтенд), выполняемые пошагово
- Сброс кэшей целевого проекта: шагом деплоя перед миграциями и сразу после правки его `.env` из панели
- Живой прогресс и лог на странице инстанса (поллинг 3с)
- Состояние рабочего дерева: текущая ветка, HEAD-коммит, отставание от remote, незакоммиченные правки, stash'и
- История последних 20 деплоев по инстансу: кто, что, когда, сколько заняло
- Ссылка на сам стенд и health-пинг его URL прямо из карточки инстанса
- Вторая ссылка на стенд через проброшенный порт (`localhost:<serve_port>`) — для доступа по ssh-туннелю
- Разграничение прав: **admin** (всё) и **tester** (только назначенные инстансы)
- Админский монитор очередей: джобы, упавшие джобы с retry/forget, активные и последние деплои (поллинг 5с),
  брошенные деплои помечены и снимаются кнопкой
- Админский список screen-сессий хоста с фильтром по пользователю (поллинг 10с)
- Просмотр и правка `.env` целевого проекта по каждому инстансу: белый список ключей, секреты маской
- Белый список путей и валидация имени ветки до запуска чего бы то ни было
- Подтверждения действий всплывают снизу экрана и гаснут сами (флеш-сообщения из `HandleInertiaRequests`)
- Тёмная тема: кнопка в шапке переключает `System → Light → Dark`, выбор помнится в браузере

## Требования

- PHP 8.2+
- Composer, Node.js и Git в `PATH` процесса **воркера очереди** (команды выполняются именно там)
- Каталоги целевых проектов доступны воркеру на чтение/запись
- Git-креды доступны воркеру неинтерактивно (см. [Windows / OpenServer](#windows--openserver))

## Установка

```bash
composer setup
```

`composer setup` = `composer install` + `.env` из `.env.example` + `key:generate` + `migrate` +
`npm install` + `npm run build`. При дефолтном `DB_CONNECTION=sqlite` файл `database/database.sqlite`
должен существовать до миграции (`touch database/database.sqlite`).

Затем — начальные пользователи и демо-инстанс:

```bash
php artisan db:seed
```

## Запуск

Разработка (сервер + воркер + логи + vite одной командой):

```bash
composer dev
```

Отдельно:

```bash
php artisan serve
```

```bash
php artisan queue:work --timeout=900
```

**Воркер очереди обязателен** — без него деплои навсегда остаются в `pending`. Держите
`--timeout` не меньше `DEPLOYER_JOB_TIMEOUT`.

Столько же касается `retry_after` у очереди: через это время очередь считает взятую джобу потерянной
и отдаёт её следующему воркеру. Ларавеловские 90 секунд для деплоя малы — второй воркер перехватил бы
ещё работающий деплой, упёрся в кэш-лок инстанса и уронил живой деплой в `failed`. Поэтому значение
по умолчанию здесь — `DEPLOYER_JOB_TIMEOUT + 300`; менять его отдельно можно через
`DB_QUEUE_RETRY_AFTER`, но держите больше таймаута джобы.

## Настройка

Глобально, через `.env` (см. `config/deployer.php`):

| Переменная | По умолчанию | Описание |
|------------|--------------|----------|
| `DEPLOYER_ALLOWED_PATHS` | `/var/www` | Префиксы путей через запятую, внутри которых обязан находиться путь инстанса. Windows-пути допустимы (`C:\OpenServer\domains\_php_8\`) |
| `DEPLOYER_TIMEOUT` | `600` | Таймаут одной команды, секунды |
| `DEPLOYER_BRANCH_CACHE_TTL` | `300` | TTL кэша списка веток, секунды |
| `DEPLOYER_COPY_EXCLUDES` | `node_modules/,vendor/,bootstrap/cache/,storage/logs/,storage/framework/{cache,sessions,views}/` | Что не копировать при дубле файлов инстанса, через запятую. `.env` исключён всегда (копируется отдельно), `.git` копируется |
| `DEPLOYER_AUTO_STASH` | `true` | Прятать локальные изменения целевого проекта в stash перед `git checkout` |
| `DEPLOYER_JOB_TIMEOUT` | `900` | Таймаут джобы, секунды (он же TTL лока деплоя) |
| `DEPLOYER_GIT_USERPROFILE` | — | Каталог профиля, подставляемый как `USERPROFILE`/`HOME` для git-подпроцессов |
| `DEPLOYER_GIT_TERMINAL_PROMPT` | `0` | `GIT_TERMINAL_PROMPT` для подпроцессов |
| `DEPLOYER_GCM_INTERACTIVE` | `Never` | `GCM_INTERACTIVE` для Git Credential Manager |
| `DEPLOYER_BACKUP_ROOT` | `/var/backups/deployer` | Каталог, в который `scripts/backup-db.sh` складывает дампы (по подкаталогу на инстанс). Подставляется в команду шага backup, предлагаемую новому инстансу; уже созданным ничего не меняет. Пустое значение — подсказки нет (на Windows пусто по умолчанию) |
| `DEPLOYER_BACKUP_KEEP` | `10` | Сколько последних дампов на инстанс оставляет `scripts/backup-db.sh`; `0` — не удалять ничего |
| `DEPLOYER_ENV_MAX_SIZE` | `262144` | Максимальный размер `.env` целевого проекта, который парсится для просмотра и правки, байты |
| `DEPLOYER_HEALTH_TIMEOUT` | `5` | Таймаут health-пинга URL инстанса, секунды |
| `DEPLOYER_SCREEN_HIDDEN_USERS` | `root` | Чьи screen-сессии не показывать на **Admin → Screens** без явного выбора в фильтре, через запятую. Пустое значение — показывать всех |
| `DEPLOYER_SERVE_COMMAND` | `php artisan serve --host=0.0.0.0 --port={port}` | Чем поднимать стенд кнопкой **Start** на **Admin → Screens**. Выполняется в каталоге инстанса внутри screen-сессии, `{port}` подставляется из настройки инстанса |
| `DEPLOYER_SCREEN_START_CHECK_DELAY` | `700` | Пауза перед проверкой, что запущенная сессия жива, миллисекунды |
| `DEPLOYER_TUNNEL_URL_TEMPLATE` | `http://localhost:{port}` | Шаблон второй ссылки на стенд — для доступа через проброшенный порт. `{port}` подставляется из `serve_port` инстанса; ссылки нет у инстансов без порта. Пустое значение убирает ссылку совсем |
| `DEPLOYER_STALE_AFTER` | `960` | Через сколько секунд молчания незавершённый деплой считается брошенным и перестаёт блокировать инстанс. Держите больше `DEPLOYER_JOB_TIMEOUT` |
| `DEPLOYER_QUEUE_WARN_AFTER` | `15` | Через сколько секунд ожидания в очереди страница предполагает, что `queue:work` не запущен |
| `DEPLOYER_NOTIFY_ON_FINISH` | `false` | Слать инициатору письмо о завершении деплоя (успех/падение). Нужна настроенная почта `MAIL_*` |
| `DEPLOYER_NOTIFY_IN_PANEL` | `true` | Показывать уведомление о завершении деплоя в панели (колокольчик в шапке) |

По инстансу, в **Admin → Instances**:

| Поле | Примечание |
|------|------------|
| `name` | Отображаемое имя |
| `path` | Абсолютный путь к развёрнутому проекту; должен пройти валидацию путей |
| `url` | Необязательный адрес стенда (`http`/`https`): ссылка «Open ↗» и цель health-пинга |
| `platform` | `linux` / `windows` — на способ запуска команд не влияет, но на Windows недоступен дубль файлов |
| `git_remote` | По умолчанию `origin`; используется для списка веток и `git pull` |
| `default_branch` | Подставляется в селект, если у рабочей копии нет текущей ветки |
| `composer_command` | Необязательно — при пустом значении шаг composer **пропускается** |
| `cache_command` | Чем сбрасывать кэши целевого проекта. По умолчанию `php artisan config:clear && php artisan view:clear && php artisan route:clear`. Выполняется шагом деплоя и после каждой правки `.env` из панели. Пустое значение — шаг пропускается, кнопки и автоматический сброс исчезают |
| `backup_command` | Чем снимать дамп БД целевого проекта. Новому инстансу панель подставляет свой `scripts/backup-db.sh` (см. ниже); пустое значение — шаг пропускается, кнопка `Backup database` не показывается. Выполняется первым шагом полного деплоя и по кнопке. Своя команда должна перенаправлять дамп в файл, иначе он целиком уедет в лог деплоя |
| `migrate_command` | По умолчанию `php artisan migrate --force` |
| `frontend_command` | По умолчанию `npm ci && npm run build` |
| `allowed_path_prefix` | Дополнительный разрешённый префикс для этого инстанса, поверх `DEPLOYER_ALLOWED_PATHS` |
| `screen_session` | Имя screen-сессии, в которой крутится стенд этого инстанса. По нему сессия сопоставляется с инстансом на **Admin → Screens** и глушится оттуда. Уникально; допустимы `A-Za-z0-9._-` |
| `serve_port` | Порт, на котором стенд слушает. Уникален; задаётся только вместе с `screen_session` |
| `is_active` | Неактивные инстансы скрыты, деплой на них невозможен |
| тестировщики | Кто из аккаунтов-тестировщиков видит инстанс и может на него деплоить |

`composer_command`, `backup_command`, `migrate_command` и `frontend_command` выполняются через системный шелл в каталоге
инстанса, поэтому синтаксис шелла (`&&`, кавычки) работает. Админ может вписать туда произвольную команду —
считайте админский доступ равносильным shell-доступу на хост.

## Действия деплоя

| Действие | Шаги | Нужна ветка |
|----------|------|-------------|
| Full deploy | backup → git → composer → cache → migrate → frontend | да |
| Code only | git | да |
| Backup database | backup | нет |
| Composer install | composer | нет |
| Clear caches | cache | нет |
| Run migrations | migrate | нет |
| Build frontend | frontend | нет |
| Clone repo | clone | нет |
| Copy files | copy → composer → cache → frontend | нет |
| Rollback | rollback → composer → cache → frontend | нет |

На странице инстанса кнопки разбиты на группы: `Deploy` (полный деплой и обновление кода),
`Individual steps` (отдельные шаги) и `Recovery` (откат).

Кнопки `Backup database`, `Composer install` и `Clear caches` на странице инстанса появляются, только когда у инстанса задана
соответствующая команда; запрос с пустой командой отклоняется. Внутри полного деплоя пустая команда
по-прежнему просто пропускает шаг — там это штатное «нечего делать», а не отказ по нажатой кнопке.

Место шага `cache` в цепочке не случайно: он идёт после composer (без `vendor` не стартует `artisan`)
и строго **до** миграций — с закэшированным конфигом `php artisan migrate` уедет в ту базу, что лежит
в `bootstrap/cache/config.php`, а не в ту, что стоит в `.env`. По умолчанию команда чистит конфиг,
шаблоны и маршруты, но не трогает `php artisan cache:clear`: на драйвере `database` он требует живого
подключения к БД и на стенде с ещё не заполненным `DB_DATABASE` уронил бы деплой. Нужен и он — допишите
в `cache_command` руками.

Шаг `backup` идёт первым — до `git`: дамп имеет смысл ровно как снимок «как было до деплоя», а после
`git pull` рабочее дерево уже другое. Упавший дамп роняет деплой на первом же шаге — до миграций дело
не доходит, и это ровно то поведение, которое нужно: не смогли снять бэкап — не трогаем базу. Команду
в лог не пишем (в ней может стоять пароль), в логе только её вывод. Долгий дамп упирается в
`DEPLOYER_TIMEOUT`, а весь деплой целиком — в `DEPLOYER_JOB_TIMEOUT`: под большую базу поднимайте оба.
Восстановление из дампа панель не делает — это ручная операция на хосте.

### `scripts/backup-db.sh`

Скрипт бэкапа лежит в самой панели и приезжает вместе с её обновлением — ставить его на хост
отдельно не нужно. Новому инстансу подставляется команда вида:

```
bash /var/www/deployer/scripts/backup-db.sh --root=/var/backups/deployer --keep=10
```

Панель запускает её в каталоге инстанса, поэтому скрипт читает `DB_*` из `.env` целевого проекта
(разбирает файл сам, а не через `source`: значение с пробелом или `$` иначе роняло бы первый шаг
деплоя) и кладёт `<БД>_<дата>.sql.gz` в `--root/<имя каталога инстанса>/`. Подкаталог можно назвать
иначе, дописав к команде слово — оно станет именем: `... --keep=10 my-project-stage`.

Каталог дампов намеренно лежит **вне** каталога инстанса. Внутри проекта дампы засоряют рабочее
дерево (их подхватывает `auto_stash` перед checkout), уезжают в новый каталог при `Copy files`
(в `DEPLOYER_COPY_EXCLUDES` их нет), а под `public/` — просто скачиваются со стенда по прямой
ссылке любым, кто угадает имя файла.

Что делает скрипт помимо самого `mysqldump`: пишет в `.part` и переименовывает только после
успеха (оборванный дамп не должен выглядеть готовым), гоняет дамп под `set -o pipefail` (иначе кодом
возврата стал бы код `gzip` и упавший дамп прошёл бы как успешный шаг), передаёт пароль временным
`--defaults-extra-file` вместо аргумента (аргументы видны в `ps` любому на хосте) и оставляет
последние `--keep` дампов на инстанс. Работает только с `DB_CONNECTION=mysql`/`mariadb`; на другом
драйвере честно падает с сообщением, а не делает вид, что забэкапил.

Разово на хосте — каталог дампов должен принадлежать тому, под кем крутится `queue:work`:

```
sudo install -d -m 700 -o www-data -g www-data /var/backups/deployer
```

Восстановление — руками:

```
gunzip -c /var/backups/deployer/my-project/app_2026-08-21_0312.sql.gz | mysql -u root -p app
```

Каждый шаг проходит `pending` → `running` → `success` / `failed` (backup и composer получают `skipped`,
если команда пустая). На первой ошибке оставшиеся шаги не выполняются, деплой переходит в `failed`, текст ошибки
дописывается в лог.

`Clone repo` стоит особняком: это разовый bootstrap рабочей копии из `Repository URL` инстанса, доступный
только админу (ссылка в списке инстансов). Тестерам это действие недоступно даже напрямую через API. Каталог
назначения (`Path`) должен быть пустым или отсутствовать и лежать внутри разрешённого префикса.

`Copy files` запускается не кнопкой на инстансе, а галочкой `Copy files from the original` в форме
`Duplicate`: панель создаёт инстанс и сразу ставит в очередь копирование каталога инстанса-источника
в `Path` нового. Требования к каталогу назначения те же, что у `Clone repo` (пуст или отсутствует,
внутри разрешённого префикса). Копируем `rsync`-ом, поэтому действие доступно только для `platform=linux`
и требует `rsync` на хосте панели. Что не копируется — `DEPLOYER_COPY_EXCLUDES`; по умолчанию это
`vendor` и `node_modules` (их ставят заново шаги composer/frontend того же деплоя) и кэши `storage`.
`.git` копируется — иначе в копию нельзя деплоить.

`.env` копируется отдельно от `rsync`: файл переносится как есть, но `DB_DATABASE` и `APP_URL` в нём
обнуляются, чтобы копия не ходила в базу и по адресу оригинала (миграция в копии сломала бы исходный
стенд). Заполнить их можно там же в панели — **Admin → Instances → Env**. Пока они пусты, копия
рабочей не станет.

По той же причине не копируется `bootstrap/cache/`: там лежит закэшированный конфиг оригинала,
и копия с ним ходила бы в базу оригинала мимо собственного `.env` — обнулённый `DB_DATABASE`
такую копию не спас бы. `packages.php`/`services.php` оттуда не жалко: их пересоберёт composer-шаг
того же деплоя, а без него Laravel допишет их сам при первой загрузке.

Лог деплоя показывает блок **Commits in this deploy** — коммиты, уехавшие на стенд, по диапазону
`commit_before..commit_after` этого деплоя (для отката — обратный диапазон, «что откатили»). Данные
подтягиваются отдельным запросом `GET /instances/{instance}/deployments/{deployment}/commits`, чтобы
git-подпроцесс не задерживал лог; у деплоев без записанных SHA блок сообщает, что данных нет.

`Rollback` возвращает рабочее дерево к `commit_before` последнего успешного полного деплоя или деплоя ветки
и пересобирает зависимости и фронт. Кнопка появляется, только когда есть к чему откатываться; доступ — как
у обычного деплоя (`deploy`-политика). Миграции не откатываются автоматически.

## Роли и доступ

| Email | Пароль | Роль |
|-------|--------|------|
| admin@local | password | admin |
| tester@local | password | tester |

(Значения из сидера — смените их.)

- **Admin**: все инстансы, CRUD инстансов и пользователей, монитор очередей, просмотр и правка `.env` инстансов.
- **Tester**: только явно назначенные инстансы; может деплоить, но не может менять конфигурацию
  и не видит `.env`.

Раздел **Activity** (`/activity`) — общая лента деплоев по доступным инстансам с фильтром по статусу.

## Ограничения безопасности

- **Валидация пути** (`PathValidator`): отклоняет пустые пути, любые с `..`, несуществующие каталоги и любой
  реальный путь вне разрешённых префиксов. Отрабатывает перед каждым деплоем и каждым получением списка веток.
  Для `Clone repo` и `Copy files` дополнительно: каталог назначения пуст или отсутствует, а его родитель
  существует и доступен воркеру на запись. Не прошедшая проверка роняет деплой в `failed` с причиной
  в логе — на Linux чаще всего это права: каталог, закрытый от `www-data`, по этим проверкам выглядит
  как несуществующий.
- **Валидация ветки**: имя должно соответствовать `deployer.branch_pattern`
  (`/^[a-zA-Z0-9_\/\.\-]+$/`), проверяется и в form request, и в `GitService`.
- **Аргументы git** передаются массивом argv (без интерполяции шеллом).
- **Параллелизм**: один деплой на инстанс одновременно (проверка в БД + кэш-лок).
- **Рейт-лимит**: 10 запросов деплоя в минуту на пользователя.
- **Просмотр `.env`**: путь инстанса проходит тот же `PathValidator`, читается только файл `.env` в его корне.
  В ответ попадают лишь ключи из `deployer.env_visible_keys`; остальные отдаются числом, без имён и значений.
  Значения ключей, подходящих под `deployer.env_masked_patterns` (`*KEY*`, `*SECRET*`, `*PASSWORD*`, `*TOKEN*`,
  `*CREDENTIALS*`, `*_DSN`), маскируются на сервере — в браузер уходит только маска.
- **Правка `.env`**: доступна только админу и только для ключей из `env_visible_keys` — ключ вне списка
  запрос отклоняет, а не игнорирует. Перевод строки в значении запрещён валидацией: иначе одно поле
  дописывало бы в файл произвольные строки. Пустое поле замаскированного ключа сервер трактует как
  «не менять», так что затереть секрет пустотой нельзя ни из формы, ни запросом мимо неё.

## Что видно на странице инстанса

- **Working tree** — что на самом деле лежит в целевом каталоге: текущая ветка, HEAD-коммит (sha, тема,
  автор, дата), `ahead`/`behind` относительно `<remote>/<branch>`, число незакоммиченных файлов и число
  stash'ей. Считается локальными git-командами без обращения к сети, поэтому `ahead`/`behind` настолько
  свежи, насколько свеж последний `fetch` (кнопка ↻ у селекта веток его делает). Блок грузится отдельным
  запросом после отрисовки страницы и не участвует в 3-секундном поллинге деплоя — он обновляется сам,
  когда деплой завершился.
- **Recent deployments** — последние 20 деплоев: время, действие, ветка, кто запустил, длительность, статус
  и код выхода. Логи в таблицу не тянутся, но клик по строке открывает лог и шаги этого деплоя
  отдельным запросом (`GET /instances/{instance}/deployments/{deployment}`). Лог можно скопировать
  или скачать файлом.
- **Зависшие деплои.** Если воркера убили посреди деплоя, строка так и останется в `running`. Через
  `DEPLOYER_STALE_AFTER` секунд молчания панель считает такой деплой брошенным: помечает его `Abandoned`,
  перестаёт опрашивать сервер и снова разрешает запуск деплоев на этот инстанс. Кнопка `Cancel` делает то
  же самое вручную — она помечает запись `failed`, но **не убивает процесс**: если он ещё жив, параллельный
  запуск всё равно не пройдёт (его не пустит кэш-лок джобы). Деплой, который слишком долго висит в `pending`,
  показывает подсказку про незапущенный `queue:work` (порог — `DEPLOYER_QUEUE_WARN_AFTER`).
  Тот же признак теперь виден и на **Admin → Queues**: в `Active deployments` брошенная строка помечена
  `Abandoned`. Раньше эта страница показывала её обычным `Running`, из-за чего давно мёртвый деплой
  выглядел работающим. Там же в каждой строке есть `Cancel` — тот же самый, что на странице инстанса,
  чтобы не обходить инстансы по одному. Админу он доступен и на выключенном инстансе: деплой могли
  бросить до того, как стенд отключили, иначе такую строку нечем закрыть.
- **Tunnel ↗** — вторая ссылка на стенд, рядом с `Open ↗`. Адрес собирается из `serve_port` инстанса
  по шаблону `DEPLOYER_TUNNEL_URL_TEMPLATE` (по умолчанию `http://localhost:{port}`) и рассчитан на тех,
  кто ходит к изолированному серверу через ssh-туннель (`ssh -L <порт>:localhost:<serve_port> ...`):
  оригинальный адрес у них не открывается, а проброшенный порт — да. Ссылка есть только у инстансов
  с заданным `serve_port` и видна всем, кому доступен инстанс. Health-пинга она не касается: он ходит
  с хоста панели, где `localhost` — сама панель, поэтому пингуется по-прежнему `url`.
  Пробрасывайте туннель на тот же номер порта, что и на сервере, — иначе стенд с прописанным `APP_URL`
  будет уводить редиректами на оригинальный адрес.
- **Health** — если у инстанса задан `url`, страница пингует его при открытии, после каждого деплоя и по
  кнопке ↻: `up` / HTTP-код / `unreachable` плюс время ответа. Пинг ходит от сервера deployer'а
  (`GET /instances/{instance}/health`, 30 запросов в минуту), доступ — по той же политике, что и сам инстанс.

## Просмотр и правка .env инстанса

**Admin → Instances → Env** показывает `.env` целевого проекта: путь файла, размер, дату изменения и таблицу
ключевых переменных. Отсутствующий, нечитаемый или слишком большой файл, как и невалидный путь инстанса,
показываются как сообщение, а не как ошибка 500.

Одно значение оттуда — `DB_DATABASE` — вынесено на карточку инстанса в списке `/instances`, строкой
`DB: <имя>`, и в таблицу **Admin → Instances** отдельной колонкой `DB`.
В отличие от самой страницы Env оно видно всем, кому доступен инстанс, включая
тестировщиков. Читается уже после отрисовки списка, отдельным запросом; недоступный `.env` даёт
`unknown`, а не ошибку.

Какие ключи видны и что маскируется — правится в `config/deployer.php` (`env_visible_keys`, `env_masked_patterns`).
Тот же список ограничивает и правку: что админ видит, то и может менять. Ключи вне списка (их число
показано внизу страницы) не отдаются наружу и не переписываются — как и комментарии, порядок строк
и кавычки: правится только значение нужного ключа, остальной файл остаётся байт в байт. Ключа в файле
нет — он дописывается в конец; оставленный пустым несуществующий ключ строку-пустышку не создаёт.

Один ключ панель пишет сама, мимо формы: `SITE_TITLE_LABEL` при каждом сохранении синхронизируется
с названием инстанса в верхнем регистре (форма его не показывает и не принимает — значение из формы
для этого ключа было бы отклонено как неизвестная переменная). Если он уже совпадает с названием,
отдельного шага не происходит; если нет — правится или дописывается вместе с остальными изменениями,
попадая в тот же `Updated: ...`.

Замаскированное значение до браузера не доезжает, поэтому поле секрета всегда пустое, а пустое поле
секрета означает «не трогать». Правило серверное, а не только в форме: устаревшая вкладка или запрос
мимо интерфейса иначе затирали бы пароль пустотой. Обратная сторона — очистить секрет из панели нельзя,
только заменить; пустое значение секрету ставят руками на хосте.

Перед каждой записью рядом кладётся `.env.backup` (предыдущая версия файла, одна). Сразу после успешной
записи панель выполняет в каталоге инстанса его `cache_command` — иначе целевой проект с закэшированным
конфигом продолжил бы жить со старой БД, а правка выглядела бы применённой. Не сработало (нет `artisan`,
путь недоступен) — правка всё равно сохранена, а причина показана отдельным сообщением. Кнопка
**Clear caches** рядом с **Save** делает то же самое отдельно — для случаев, когда `.env` правили руками
на хосте (`POST /admin/instances/{instance}/caches/clear`). У инстанса с пустой `cache_command` не
запускается ни то, ни другое.

Если у инстанса заданы `screen_session` и `serve_port` (см. [Screen-сессии хоста](#screen-сессии-хоста))
и его сессия в этот момент запущена, сохранение `.env` её перезапускает тем же `stop()`+`start()`, что
и кнопки на **Admin → Screens** — `artisan serve` держит переменные окружения в памяти процесса и
подхватывает `.env` только заново стартовав. Погашенную сессию так не поднимаем: правка `.env` не повод
включать стенд, который выключили осознанно. Не получилось перезапустить — правка всё равно сохранена,
причина показана отдельным сообщением, как и с чисткой кэша.

Если `.env` в каталоге нет, страница предлагает его завести: пустым или копией `.env.example`
(кнопка появляется, только когда пример действительно лежит рядом). Существующий `.env` этим действием
не перезаписывается ни при каких условиях — чтобы стереть боевые значения, файл придётся сначала удалить
руками на хосте. После создания страница сразу открывается формой, и значения заполняются как обычно.

## Screen-сессии хоста

**Admin → Screens** показывает живые screen-сессии на хосте панели: pid, владелец, имя сессии (аргумент
`-S`), время старта, аптайм и полная команда. Обновляется каждые 10 секунд, список приезжает отдельным
запросом и не задерживает отрисовку страницы.

Данные берутся из таблицы процессов (`ps -C screen,SCREEN`), а не из `screen -ls`. Причина: каталог
сокетов screen'а (`/run/screen/S-<user>`) имеет режим `0700` и читается только своим владельцем, поэтому
`screen -ls` из-под пользователя панели показал бы пустоту, даже если сессии есть. `ps` же читает `/proc`
и видит процессы всех пользователей — никаких прав, sudo и правки прав на сокеты не нужно.

Плата за это — **нет колонки Attached/Detached**: это состояние живёт в сокете, а не в процессе. Так же
не видно имени вида `pid.tty.host` у сессий, запущенных без `-S`, — в argv его просто нет, у таких строк
имя пустое.

Сессии `root` по умолчанию скрыты (`DEPLOYER_SCREEN_HIDDEN_USERS`): под ним обычно крутятся системные
демоны, а не стенды. Из фильтра пользователь при этом не пропадает — выберите его, и его сессии
покажутся; в шапке списка видно, сколько строк скрыто.

Страница доступна только админу. На Windows-хосте вкладка честно сообщает, что `screen` и `ps` там
недоступны. Если `/proc` смонтирован с `hidepid=2`, чужие процессы не видны и список сведётся к сессиям
самого пользователя панели.

### Запуск и остановка стендов

Инстансу можно задать имя screen-сессии и порт (`screen_session`, `serve_port` в **Admin → Instances**).
Тогда на **Admin → Screens** появляется:

- селект **Start an instance** — поднимает стенд командой `DEPLOYER_SERVE_COMMAND` внутри
  `screen -dmS <screen_session>`, в каталоге инстанса (`POST /admin/screens`). В списке только те
  инстансы, чья сессия сейчас не запущена;
- колонка **Instance** — сессия, чьё имя совпало с `screen_session` инстанса, показана ссылкой на него;
- кнопка **Stop** в каждой строке — `screen -S <name> -X quit` (`DELETE /admin/screens`), с
  подтверждением. Работает и для сессий, не связанных с инстансами.

Команда запуска выполняется как `bash -lc`, то есть логин-профиль подтягивается — так находится нужный
`php`. Сессия живёт ровно столько, сколько живёт команда внутри: упавший `artisan serve` не оставляет
пустую сессию, которая выглядела бы работающей. Поэтому после старта панель ждёт
`DEPLOYER_SCREEN_START_CHECK_DELAY` миллисекунд и проверяет, что сессия действительно есть — сама
`screen -dmS` выходит с нулём в любом случае и об упавшей команде не сообщает.

Важное ограничение: **глушить можно только сессии того пользователя, под которым работает панель.**
В отличие от чтения списка, `screen -X` ходит в сокет (`/run/screen/S-<user>`, режим `0700`), поэтому
чужую сессию screen объявит несуществующей — панель покажет эту ошибку как есть. Сессий, поднятых
самой панелью, это не касается: их владелец — она же. А вот стенды, запущенные руками из чужого
логина, останутся видимыми в списке, но не глушимыми — перезапустите их через панель один раз, и
дальше они будут под её управлением.

## Windows / OpenServer

Деплои выполняются от пользователя PHP/воркера, у которого на Windows обычно нет своих git-кредов.
Укажите нужный профиль:

```
DEPLOYER_GIT_USERPROFILE=C:\Users\YourUser
```

`GIT_TERMINAL_PROMPT=0` и `GCM_INTERACTIVE=Never` проставляются подпроцессам по умолчанию, чтобы при
отсутствии кредов команда падала сразу, а не вешала воркер на невидимом запросе пароля.

Не забудьте добавить Windows-корень в белый список, например:

```
DEPLOYER_ALLOWED_PATHS=/var/www,C:\OpenServer\domains\_php_8\
```

## Диагностика

**`fatal: unable to access '...': getaddrinfo() thread failed to start`** — git-подпроцесс стартовал без
`SystemRoot`, из-за чего Winsock на Windows не поднимает поток резолвера. `ProcessRunner` теперь явно
прокидывает системные переменные (`INHERITED_ENV_KEYS`); если ошибка вернулась — проверьте, что нужная
переменная есть в этом списке.

**Пустой список веток** — причина показывается прямо под селектом на странице инстанса (несуществующий путь,
путь вне разрешённых префиксов, недоступный remote).

**Белая страница при открытом приложении** — остался `public/hot` от прошлой сессии `npm run dev`, и
приложение тянет ассеты с несуществующего дев-сервера. Либо запустите `npm run dev`, либо удалите
`public/hot`, чтобы вернуться к собранным файлам из `public/build`.

## Известные ограничения

- Прогресс доставляется поллингом, без websockets/SSE; вывод дописывается в колонку `deployments.output`
  на каждый чанк, поэтому «болтливые» команды дают много записей в БД.
- Грязное рабочее дерево уходит в stash автоматически, но стопка stash'ей в целевом проекте
  никогда не разбирается — панель показывает счётчик, разбирает его по-прежнему человек.
- Health-пинг — это один синхронный `GET` по URL инстанса без ретраев: он говорит «отвечает / не отвечает»,
  а не «работает правильно». Адрес задаёт только админ, схема ограничена `http`/`https`.
- `Cancel` и автоматическая пометка брошенного деплоя правят только запись в БД. Убить сам процесс на хосте
  панель не умеет — если воркер ещё жив, он доработает до конца или до `DEPLOYER_JOB_TIMEOUT`.
- `platform` на способ запуска команд не влияет; единственное, на что он смотрит, — запрет копирования
  файлов на Windows-инстансе.
- Дубль файлов работает только на Linux и требует `rsync` на хосте панели; копия делается локально,
  копирование на другой хост панель не умеет.
- Screen-сессии видны только на хосте самой панели и только на чтение: ни attach, ни kill из панели нет,
  колонки Attached/Detached тоже нет (см. [Screen-сессии хоста](#screen-сессии-хоста)).
- Один remote на инстанс. Правка `.env` ограничена ключами из `env_visible_keys`: удалить ключ,
  добавить новый сверх списка или очистить замаскированный секрет из панели нельзя. Под ветку
  или окружение `.env` панель не переключает.
